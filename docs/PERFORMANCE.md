# go_tsh 性能报告

> 数据采集于本机，非实验室环境；绝对值仅供量级参考，
> **同一台机器上的前后对比才是这份报告的主要价值**。

## 测试环境

| 项 | 值 |
| --- | --- |
| CPU | Intel Core Ultra 7 155H（22 逻辑核） |
| 操作系统 | Windows 11 |
| Go | go1.27.1 windows/amd64 |
| 编译器 | MSYS2 GCC 16.2.0（`ucrt64`），仅 `-race` 需要 |

## 方法

**语料**：`corpus.Generate(100000)` 合成 10 万篇，固定随机种子因而可复现。

实测索引规模：

```
100,000 篇 / 200,110 个词条 / 索引约 193.9 MB / 构建耗时约 15.4s
```

语料刻意做成**不均匀**的词频分布——每篇只从词表里抽 3–8 个主题词并重复使用，
再叠加只出现一两次的生僻词。若每篇都从整个词表独立随机抽词，
所有词的 df 都会趋近于 N，posting 长度全部相等，测出来的分支与缓存行为是失真的。

**测量路径**：`httptest.NewServer` 起真实监听 + 真实 `net/http` 客户端，
因此**包含** TCP、请求解析、路由、中间件与 JSON 序列化。
直接调 `Engine.Search` 会把这些全部漏掉，数字会偏乐观。

**⚠️ 关于 P50**：本机 harness 的逐请求 `time.Since` 出现了亚微秒伪影——
约一半样本读数为 0，与 `ns/op` 均值自相矛盾（例如均值 287µs 而 p50 读数为 0）。
**因此本报告不采用 P50，请以「均值 / P95 / P99 / 最大值」为准。**
原始分位数已打进 benchmark 日志，可用 `-v` 查看。

## 单连接延迟

10 万篇语料，每项 2000 次请求，串行。

| 场景 | 均值 | P95 | P99 | 最大 | 分配/请求 |
| --- | --- | --- | --- | --- | --- |
| 单词检索 `q=inverted` | 1.00 ms | 2.32 ms | 6.51 ms | 27.8 ms | 378 KB |
| 短语 `"inverted index"` | 1.78 ms | 4.55 ms | 8.25 ms | 140 ms | 214 KB |
| 布尔 `inverted AND index` | 1.73 ms | 3.52 ms | 12.4 ms | 47.9 ms | 851 KB |
| 带高亮 | 2.40 ms | 5.03 ms | 14.8 ms | 383 ms | 567 KB |
| 生僻词 `q=rare00042` | 0.55 ms | 1.53 ms | 4.35 ms | 9.5 ms | 29.9 KB |
| `GET /api/v1/stats` | 0.24 ms | 1.01 ms | 1.93 ms | 5.4 ms | 6.4 KB |
| `PUT /api/v1/documents/{id}` | 0.27 ms | — | — | — | 11.8 KB |

**所有检索路径的 P99 都低于 20 ms 的验收线。**

## 并发吞吐

10 万篇语料，`b.RunParallel`，22 逻辑核，跑 3 秒。
`ns/op` 是聚合值，其倒数即吞吐。

| 场景 | 聚合 ns/op | 吞吐 |
| --- | --- | --- |
| 并发检索 | 197 µs | **≈ 5,100 req/s** |
| 并发短语检索 | 275 µs | ≈ 3,600 req/s |
| 并发写入 | 52 µs | **≈ 19,400 req/s** |

并发检索相对单连接的加速比约 **5 倍**，明显低于核心数。
主要限制是**分配速率**：378 KB/请求 × 5,000 req/s ≈ 1.9 GB/s，
GC 成为瓶颈，而不是索引的读锁。

## 压测抓到的真实缺陷

**`/api/v1/stats` 曾经是 O(索引规模)。**

它的 `IndexBytes` 靠每次请求全量遍历 terms 与 postings 计算，
10 万篇下要跑约 1500 万次循环：

| | 修复前 | 修复后 |
| --- | --- | --- |
| `GET /api/v1/stats` 均值 | **121 ms** | **0.24 ms** |
| P95 | 196 ms | 1.01 ms |
| P99 | 401 ms | 1.93 ms |

**一个监控端点做成 O(n)，在真实索引规模上根本不能用**——
恰恰是压测才能暴露出来，功能测试和单元基准都看不到。
修复方式是把内存估算改成**增量记账**：写入路径上加、删除路径上减，
`Stats()` 变成 O(1)。账目精确到「写入再删除后回到 0」，有专门用例守着。

## 已知限制

**单次检索的分配量与命中数成正比。**

求值器会在内存里物化完整的命中集合（`hitList`），
再交给 Top-K 挑选。对命中 1 万篇的查询，这一趟要分配约 12 字节 × 命中数的数倍。
实测 `q=inverted`（df ≈ 9,000）时 378 KB/请求。

后果：
- 命中集越大，GC 压力越大，并发吞吐上不去；
- 极端情况下（某个词出现在几乎所有文档里）单请求可达数 MB。

**改进方向**：把求值器从「物化切片 + 归并」改成「迭代器 + 流式送入 Top-K」，
让内存占用与 `limit` 而非命中数成正比，而不是与命中数成正比。
当前设计是「先正确、可验证，再谈极致」，且已在验收线内。

## 持久化：日志增长与重启代价

**这一节是选型与容量规划最该先看的数据。**

L1 持久化是**只追加**的原文日志，没有压实（快照/截断）。日志里存的是
「历史上发生过的每一次写入」，而不是「当前有哪些文档」。
后果是两个效应叠加：

### 实测（5000 篇、正文约 461 字节、标准分析器）

| 场景 | 日志/数据 | 重启重放 | 单条记录重放 |
| --- | --- | --- | --- |
| 从不更新 | **1.1 倍** | **335 ms** | 67 µs |
| 每篇更新 10 次 | **11.6 倍** | **11.3 s** | 206 µs |

两个效应：

1. **记录数 = 历史写入总次数**，不是文档数。更新 10 次就是 11 倍的记录；
2. **更新一条已有文档比新建一条贵 3 倍**（206 µs vs 67 µs）——
   重放时要先把旧版本的全部词条摘除，再写入新版本。

两者相乘，重启代价是「从不更新」的 **34 倍**。

### 线性外推（不压实时）

| 文档数 | 从不更新 | 每篇更新 10 次 |
| --- | --- | --- |
| 1 万 | 1.4 s | 23 s |
| 10 万 | 7 s | **3 分 47 秒** |
| 100 万 | 1 分 7 秒 | **37 分 48 秒** |

日志体积同样按同样比例膨胀：10 万篇 + 10 次更新 → **约 509 MB**。

> 这不是「可能发生」，而是**必然发生**——只要服务在持续接收更新。
> 对 MVP 用户尤其致命：他们不会去运维一个搜索服务，只会发现
> 「重启越来越慢」，然后在某次重启时放弃。

### 压实后的实测对比

**压实已实现**：日志会被重写成「当前状态的快照」。
同样的负载（5000 篇 × 10 次更新）、同一台机器：

| | 压实前 | 压实后 |
| --- | --- | --- |
| 日志 / 数据 | 11.6 倍 | **1.1 倍** |
| 日志大小 | 25.43 MB | **2.32 MB** |
| 日志记录数 | 55 000 | **5 001** |
| **重启重放** | **11.3 s** | **263 ms** |

重启快 **43 倍**，日志体积与重放条数都回到「从不更新」的量级
（263 ms 对 335 ms）。

**代价**：同一批写入 14.2 s → 15.7 s（**+10.6%**）。自动压实挤在正常
写入路径上完成，不额外占用停机时间。

**触发条件**：日志记录数 > 存活文档数 × **3**，且总记录数 > **512** 条。
用记录条数而不是字节数——真正拖慢重启的是要重放的条数（每条都要走一遍
分析、还要摘除旧版本），而字节数还受文档长度干扰。

**锁的边界**：序列化全部存活文档时**不持任何锁**。那一步可能要写几百 MB，
锁住它等于把所有写请求停住好几秒。只有「接上压实期间新产生的增量记录 +
fsync + 改名替换」这一段持锁，且与索引大小无关。

## 内存：每篇文档占多少

纯内存索引，**数据量直接受 RAM 限制**。标准分析器，20000 篇实测：

| 正文长度 | 每篇内存 | 相对正文 | 2 GB 预算约可装 |
| --- | --- | --- | --- |
| 短（约 50 字 / 144 B） | **1 537 B** | 10.7 倍 | **约 139 万篇** |
| 中（约 500 字 / 1.4 KB） | **3 216 B** | 2.2 倍 | 约 66 万篇 |
| 长（约 5000 字 / 14 KB） | **20 496 B** | 1.4 倍 | 约 10 万篇 |

**短文本的放大率最高（10.7 倍）**：词条倒排、每文档的字段长度表、
DocID 映射这些固定开销摊到小文档上就显得很大。

启用中文分析器还要再加约 **108 MB** 的词典基线。

> 这些数字是「能不能用」的第一道门槛，README 里应当直接给出，
> 而不是让用户自己去压测。

## 中文分析器的代价

引入 `-analyzer chinese` 后的实测数据（同机）：

| 项 | 数值 |
| --- | --- |
| 词典加载（`zh_s`） | **732 ms** |
| 内存基线（词典常驻） | **约 108 MB** |
| 二进制体积（linux/amd64） | 6.71 MB → **38.47 MB** |
| 纯汉字文本分析 | 27,703 ns/op，**12.13 MB/s** |
| 中英混排分析 | 50,806 ns/op，**9.53 MB/s** |
| 纯英文文本（经中文分析器） | 74,570 ns/op，**17.14 MB/s** |

对照组：同一台机器上，纯英文文本经**标准分析器**处理为
77,555 ns/op、16.48 MB/s。

**两者基本持平**——中文分析器在非汉字段上只是转发给标准规则，没有额外开销。

> ⚠️ **一条测量教训**：我最初把这两次数据放在**不同运行**里比较，
> 得出「中文分析器的英文路径慢 2.7 倍」的错误结论。
> 实际上那次运行加载了 108 MB 词典，**词典的内存压力本身就让分析吞吐接近腰斩**。
> 涉及大内存结构的基准，必须在同一次运行内对比，否则测的是内存环境而不是代码。

### 索引形态

同一篇中文文档（约 130 字）分别用两个分析器建索引：

| 分析器 | 词条数 | 索引体积 |
| --- | --- | --- |
| `standard`（逐字） | 69 | 4341 字节 |
| `chinese`（词级） | 34 | 2545 字节 |

词条数少 51%，体积少 41%。**这是中文分析器的主要收益来源**——
不是召回，召回上两者一致（见 [docs/CHINESE.md](docs/CHINESE.md)）。

### 体积的退路

```bash
go build -tags ne ...   # 不内嵌词典
```

实测 **7.61 MB**，比内嵌版省 **30.86 MB**。
代价是词典需要外部提供，当前代码走的是内嵌路径，切换需额外改造。

## 复现方式

```powershell
$env:GOCACHE = "$PWD\.gocache"
$go = "D:\Program Files\Go\bin\go.exe"

# 单连接延迟（含 P95/P99/最大值，原始分位数见 -v 日志）
& $go test -run '^$' -bench 'BenchmarkHTTPGet' -benchmem -benchtime 2000x -v ./pkg/httpapi

# 并发吞吐
& $go test -run '^$' -bench 'BenchmarkHTTPParallel' -benchmem -benchtime 3s ./pkg/httpapi

# 纯引擎层（不含 HTTP）
& $go test -run '^$' -bench 'BenchmarkSearch100k' -benchmem ./internal/query
```
