# 中文分词与检索

## 启用

```powershell
tshd -analyzer chinese
tshd -analyzer chinese -dict ./words.txt   # 再追加领域词
tshd -analyzer chinese -no-sub-words       # 关掉子词扩展，索引更小
```

`analyzer` 决定索引里存的是什么词条，因此**换分析器必须重建索引**。
本项目是内存索引，改完参数重启即可。

---

## 两个分析器到底差在哪（实测）

这是本节最值得先读的部分，因为直觉在这里很容易出错。

### 反直觉的事实：标准分析器对中文并不差

默认的 standard 分析器把汉字**逐字**索引（`isUnigramScript` 分支直接
产出词条，绕过 `MinTokenLen` 过滤——汉字单字本身有意义）。

关键在于**执行器怎么用这些单字**。`evalTerm` 里：

```go
default:
    // 一个词被切成多个 token，例如 "full-width" -> full + width。
    // 按短语处理最符合直觉：用户写的是一个整体，不应拆成 OR。
    return s.evalPhraseTokens(v, tokens, fields)
```

裸词被拆成多个 token 时，**按短语求值**，位置必须连续。

于是标准分析器对中文做的其实是**逐字连续匹配**，本质上等价于子串匹配。
实测：文档「全新文档搜索系统」不会被「全文搜索」召回，
因为 `全@0` 与 `文@2` 不相邻。

**所以：中文检索在引入中文分析器之前就是可用的，两者在连续汉字的召回上一致。**

### 真正的差别在索引形态

同一篇文档，两个分析器的产出：

| 分析器 | 词条数 | 索引体积 | 词条形态 |
| --- | --- | --- | --- |
| `standard` | **69** | 4341 字节 | 逐字：全 文 搜 索 的 是 在 … |
| `chinese` | **34** | 2545 字节 | 词级：全文 搜索 服务 倒排 索引 … |

词条数少 **51%**，索引体积少 **41%**。

更关键的是**高频功能字**：「的」「是」「在」在逐字索引里是正式词条，
它们的逆文档频率接近 0（对排序几乎没有贡献），
却让每次包含它们的查询都要扫描长度接近文档总数的 posting 列表。
中文分析器按 `MinTokenLen=2` 把单字词过滤掉，这个问题就不存在。

**结论：中文分析器的收益是索引体积、查询开销与排序质量，不是召回。**

## 设计

```
字节游标扫描
  ├─ 连续汉字 → gse 词典分词
  └─ 其余部分 → 整块交给 StandardAnalyzer（规则完全不变）
```

只有中文换了算法，英文侧已有的行为——小写化、词内撇号、全角折叠、
停用词过滤、最小词长——原样保留。过滤规则收敛在 `keep()` 一处实现，
避免中英文两侧的口径日后走偏。

### 位置语义

与英文侧一致：**每个词占一个位置，被过滤掉的词同样占位**。
这样中英混排时位置序列不会错乱，短语查询才能正常工作。

### 子词扩展

长词（runes ≥ 3）会用 `CutSearch` 取出子词一并入索引，
「大学」因此能命中「大学生」。

**子词与父词共享同一个位置**，这是 Lucene `SynonymGraphFilter` 的语义：
短语查询在词级与子词级都能正确对齐，而不会因为插入子词把后续位置整体推后。

代价：当查询把一个子词和后面的词拼成短语时，可能命中原文中并不相邻的组合。
这是换取子词召回所付出的代价，属已知取舍。用 `-no-sub-words` 可以关掉。

## 实测代价

| 项 | 数值 |
| --- | --- |
| 词典加载 | **732 ms**（`zh_s`，仅简体） |
| 内存基线 | **约 108 MB** |
| 二进制体积 | 6.71 MB → **38.47 MB** |
| 纯汉字文本分析吞吐 | 约 12 MB/s（英文约 17 MB/s，同一次运行内对比） |

### 词典选择

| 词典 | 加载 | 堆增长 |
| --- | --- | --- |
| `zh`（简+繁） | 1.475 s | 169.8 MB |
| **`zh_s`（仅简体）** | **732 ms** | **107.9 MB** |
| `zh_t`（仅繁体） | 558 ms | 100.6 MB |

当前用 `zh_s`。繁体场景不在目标内，没必要为此付双倍内存。

### 体积的退路

内嵌词典约 30 MB，占二进制增长的绝大部分。若部署对体积敏感：

```bash
go build -tags ne ...
```

实测 **7.61 MB**（省 30.86 MB），但词典不再内嵌，
需要自行提供词典文件并改用 `gse.New(...)` 加载。
当前代码走的是内嵌路径，切换到 `ne` 需要额外改造——这是一个**取舍点**，
不是现成开关。

### 自定义词典的成本

`AddToken` 只往 trie 里写，**不会**更新最短路径所需的词频统计与子词缓存，
少了 `CalcToken()` 新词根本不会被选中。

而 `CalcToken()` 是 O(词典规模)，还会重算全部 58.7 万词条的子词缓存，
实测约 0.5 秒。因此它只能在所有词条加完之后**调用一次**，
绝不能放进循环里。

## 已知小问题

**`LoadDict` 失败时会绕过 `SkipLog` 打一行日志。** gse 的 `LoadDict` 在
文件路径分支里直接用 `log.Println` 输出，不受 `Segmenter.SkipLog` 控制。
词典文件缺失时除了返回错误，stderr 上也会多一行 gse 的日志。
不影响正确性，但在库场景下不够干净——错误已经通过返回值完整传出来了。

## 踩坑记录

这几条都是「先想当然、后被实测推翻」的，记下来避免重犯。

1. **搜索模式不是 `ModeSegment`。** 我最初用它，发现它与精确模式输出**完全相同**，
   且 `Token().Segments()` 返回的子词偏移是**共享缓冲区**——「万岁」的子词居然是
   「中」「华」。读 gse 自己的测试才纠正为 `CutSearch`（返回扁平子词列表）。
   靠猜 API 会写出完全错误的东西。

2. **子词会重叠。** 「中华人民共和国」的子词是
   `中华[0,6) 华人[3,9) 人民[6,12) 共和[12,18) 共和国[12,21)`，
   简单的顺序扫描定位不了偏移。现在的做法是在**词内**用最早匹配定位——
   中文词很短，重复字导致的歧义影响有限，且结果确定可复现。

3. **中文分析器并没有"让中文检索从不可用变可用"。** 我曾据
   「单字被 MinTokenLen 过滤」推断标准分析器产不出中文词条，
   实测是 `[全 文 搜 索 服 务]`——`isUnigramScript` 分支绕过了长度过滤。
   差一点把一个错误结论写进文档。

4. **单字索引并不像想象中那样容易误召回。** 我以为「全新文档搜索系统」
   会被「全文搜索」误召回，实测不会——裸词按短语求值，要求位置连续。
   默认操作符是 AND 这一点也影响了我最初的分析。

5. **跨运行对比基准会得出错误结论。** 我曾据两次不同运行的 MB/s 判定
   中文分析器的英文路径慢 2.7 倍；在同一次运行内对比，两者持平
   （17.14 vs 16.48 MB/s）。差异来自其中一次加载了 108 MB 词典带来的内存压力。
   **加载大词典本身就会让分析吞吐接近腰斩**，这个才是真实现象。
